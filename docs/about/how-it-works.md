# Security Intelligence Libraryの仕組み

**重要なセキュリティ情報を、経営判断と現場の対策に役立つ知識へ。** Security Intelligence Library（SIL）は、ニュースを大量に並べるサイトではありません。公開された一次情報を中心に、企業のリスクやセキュリティ対策にとって何が変わるのかを整理し、記事として残します。

このページでは、候補情報の収集から記事公開、月次・四半期レビューまでを説明します。詳細な編集基準や運用上の定義は、[About / Editorial Policy](index.md) と [Selection Policy](https://github.com/peridotan/security-intelligence-library/blob/main/SECURITY_INTELLIGENCE_SELECTION_POLICY.md) を参照してください。

## 1. 全体の流れ

| 段階 | 何をするか | 主な役割 |
| --- | --- | --- |
| **1. 収集** | 政府・標準化団体・セキュリティ研究者等の公開情報を集める | GitHub Actions、補完調査、人間 |
| **2. 照合** | 既存記事や採択済み候補との重複、実質的な新情報を確認する | 自動処理＋AI支援＋人間 |
| **3. 振り分け** | Library / Vulnerability / Watchの扱いを検討する | 自動ルール＋人間 |
| **4. 選定** | 経営・現場への影響などを評価し、記事化・更新・保留を決める | **人間が最終判断** |
| **5. 記事化・根拠確認** | 日本語の記事案を作成し、重要な事実と出典を照合する | AI支援＋人間によるEvidence Review |
| **6. 公開・再評価** | 承認した記事を公開し、月次・四半期で横断的に分析する | 人間＋GitHub Actions |

情報は収集した時点で公開されるわけではありません。自動処理は候補づくりと確認を支援し、**テーマの採用、根拠の実質的な確認、記事の公開は人間の判断を必要とします**。

## 2. どこから情報を収集するのか

対象は、Cybersecurity、Identity Security、AI Security、Regulation、Risk Managementです。主に次のような公開情報を参照します。

- **政府・規制当局・標準化団体**：法令・制度、ガイダンス、公式仕様、注意喚起
- **国内外のCERT・公的機関**：インシデントや脆弱性の注意喚起、組織向け対策情報
- **セキュリティ研究チーム・技術ベンダー**：攻撃の観測、技術分析、防御手法や新たなリスク

情報源には優先順位があります。公的・公式な一次情報を優先し、ベンダー調査は観測範囲を明示します。メディア報道は可能な限り原資料で照合し、SNSや攻撃者の主張は未検証情報と区別します。

あらかじめ登録した情報源はGitHub Actionsで候補収集します。また、**登録済みフィードだけでは拾いきれない重要情報を補完調査で探す**場合もあります。これは網羅性を保証するものではなく、重要性と出典の質を重視する方法です。

詳しい収集元は[情報源の設定](https://github.com/peridotan/security-intelligence-library/blob/main/config/intelligence_sources.yml)で確認できます。

## 3. ニュースをすべて記事にするわけではない

候補が見つかったら、記事のURLだけではなく、同じ事件・調査・制度・製品・CVE・重要な発見がすでにLibraryに存在するか確認します。

新しい情報は、新規記事にするとは限りません。既存記事に重要な進展があれば**その記事を更新**し、重複なら新しい記事は作りません。情報が十分に確かでない場合は保留します。

さらに、候補は主に次の3つに振り分けます。

| 振り分け先 | 扱う情報の特徴 |
| --- | --- |
| **Library** | 技術や製品を超え、企業のセキュリティ対策やリスク管理に継続的な示唆がある情報 |
| **Vulnerability Intelligence** | 個別製品やCVE、脆弱性の深刻度・実悪用状況などを中心に追う情報 |
| **Watch** | 関連性はあるが、影響範囲や根拠を追加確認する必要がある情報 |

例えば、個別製品のパッチ公開は通常Vulnerability Intelligenceに適しています。一方、その事例から広く共通するIdentityやサプライチェーンの管理課題が見える場合は、Libraryの記事候補になることがあります。

**振り分けは記事の掲載決定ではありません。** 自動ルールによる一次分類の後も、人間が内容と判断理由を確認します。

## 4. 何を重要と判断するのか

Libraryでは、次の5軸で候補を比較する**100点満点の試行評価**を導入しています。

| 評価軸 | 配点 | 着目点 |
| --- | ---: | --- |
| 経営・事業への影響 | 30点 | 事業継続、説明責任、投資・優先順位への影響 |
| セキュリティ対策への影響 | 25点 | 設計、運用、検知、統制を見直す必要性 |
| 新規性・変化の大きさ | 20点 | 既知情報と比べた新しい事実や構造変化 |
| 日本企業への関連性 | 15点 | 国内の企業、制度、技術・取引関係への適用可能性 |
| 根拠の確かさ | 10点 | 重要な主張を原資料に遡って確認できるか |

**この点数は選定を支援するための目安であり、機械的な採用条件ではありません。** 75点以上は積極的な検討対象、55〜74点は人間が採用・更新・追加調査・保留を個別判断する帯域です。低得点でも緊急性が高ければ優先審査します。逆に、高得点でも重複や根拠不足があれば新規掲載しません。

また、**重要性・緊急性・根拠の確かさは異なるもの**として扱います。将来の投資判断に重要な情報が、必ずしも今日対応すべき情報とは限りません。

詳しくは[情報収集・選定基準の詳細](https://github.com/peridotan/security-intelligence-library/blob/main/SECURITY_INTELLIGENCE_SELECTION_POLICY.md)をご覧ください。

## 5. AIはどこまで関わるのか

生成AIは、補完調査、論点整理、記事案の作成、比較分析、根拠の照合補助に利用します。一方で、**AIの出力をそのまま事実として掲載しません**。

記事化する際は、一次資料に基づく事実、資料の発行元による観測・推測・主張、本Library独自の分析を区別します。特に重要な主張については、出典URLや該当するページ・節を記録する *Evidence Review* を用意します。

- **source_fact**：一次情報で確認できる具体的な事実
- **source_claim**：調査主体・ベンダー等による主張や予測
- **library_assessment**：本Libraryの解釈や推奨対応（推論理由を説明）

AIが根拠を照合することと、人間がその内容を確認・承認することは別です。新たに公開する記事では重要な主張を人間が確認し、未解決の根拠を修正・保留したうえで公開の可否を判断します。

## 6. 公開した情報をどう活用するのか

記事は単独で終わらせず、異なる時間軸から読み直せるようにしています。

| ページ | 読み方 |
| --- | --- |
| [Current Intelligence](../index.md) | いま注目すべきテーマを知る |
| [Monthly Intelligence](../monthly/index.md) | その月の重要な変化を俯瞰する |
| [Quarterly Review](../quarterly/index.md) | 3か月の情報を横断し、構造的な変化を理解する |
| [Topics](../topics/index.md) | AI Agent、Identity、Supply Chainなど論点別に関連情報を読む |

月次・四半期のテーマは記事の点数順に機械的に選ぶのではなく、その期間に何が変わり、どのような意思決定に影響するかを再分析します。公開後も重要な新事実・仕様変更・制度変更があれば記事を再確認し、必要に応じて更新または後継記事へ誘導します。

## 7. この仕組みが保証しないこと

SILは、すべてのセキュリティニュース、脆弱性、インシデントを網羅するものではありません。公開情報や観測データには遅れ、不確実性、偏りがあります。ベンダーの観測結果を、そのまま全企業や日本国内の実態として一般化することもしません。

また、GitHub Actionsのチェック成功は、記事の主張がすべて正しいことを証明しません。重要な判断の前には、記事の出典と最新の一次情報も確認してください。

編集上の責任、Evidenceの考え方、公開情報の取扱いについては[About / Editorial Policy](index.md)を参照してください。
